# Call Summary v2

The notification pipeline is `Call Data → Structured Extraction → Validation → Deduplication → HTML Rendering → Email Delivery`.

## Components and boundaries

- `workers/notifications/src/summary.mjs`: explicit Zod schemas, Italian extraction, evidence references, English translation of original spoken turns, source alignment, normalization, rendering and plain-text alternative.
- `workers/notifications/src/provider.mjs`: paginated, read-only Telnyx conversation lookup; Telnyx-hosted inference; validates delivery acknowledgements.
- `scripts/patch-phone-summary.mjs`: guarded patch of the existing phone Worker's notification sender/query and its notification scheduling. Does not change call control, signatures, outbound approval, voice, DTMF, inbound routing or Telnyx configuration.
- `apps-script/summary-v2.gs`: v2 email delivery appended to the existing Google Apps Script project, using its existing recipient and `WEBHOOK_SECRET` authentication. The request cannot override the recipient.
- `scripts/patch-apps-script-summary.mjs`: inserts the v2 dispatch **after** existing authentication. Legacy delivery remains available during rollout/rollback.
- `scripts/prepare-summary-release.mjs`: produces private deployment files from private production snapshots. No original phone source, owner address, resource credentials or full conversations are committed.

The existing D1 columns were inspected before the change. Only existing notification lease/status/attempt fields are used. No schema migrations or historical-data updates are required. Structured v2 data is computed for delivery; technical records and original instructions remain in their existing backend fields and are not appended to the main email.

## Data and correctness

The schemas distinguish the technical call status from `successful`, `partially_successful`, `unresolved`, and `failed` task outcomes. A carrier `completed` result is never sufficient evidence of task success. Extraction uses the recorded conversation and, for outbound, the owner's task snapshot as context; that context is not evidence that a fact occurred or that the remote business identified itself.

Claims carry exact quotes and source IDs. Unsupported identities, facts and next actions are dropped. Outcome and next-action evidence must refer to the remote party. Facts are normalized and deduplicated but the renderer does not repeat a separate facts/conclusion section. A concrete, agreed next action is optional; generic advice is not rendered.

Translation is per source turn, with source IDs and original text attached by the backend rather than regenerated by the model. Results are reassembled in chronological order. Standard Japanese numbered-menu options are translated independently and rebound to their original digits in code. Supported system events are mapped explicitly; system prompts and tool payloads are excluded. The original language is not repeated in the email. Retrieved pages are bounded; uncertain completeness is marked partial, never full. Missing original turns produce `Full transcript unavailable`; a summary is never expanded into invented dialogue.

SQLite timestamps without a zone are interpreted as UTC. Email dates use `Asia/Tokyo`, with an authoritative `started_at` preferred and the first available conversation timestamp used when it is missing. Invalid dates and unknown durations are disclosed rather than guessed. Dynamic subjects contain the identified party and actual outcome; they do not reuse the old UTC-based date subject.

Extraction currently uses `meta-llama/Llama-3.3-70B-Instruct` through Telnyx's chat-completions endpoint with JSON Schema output. Model selection is configurable as `SUMMARY_MODEL`. No new model vendor, API credential, or Telnyx assistant configuration is needed. Live API probes verified hosted-model availability and schema output; JSON-object mode alone produced inadequate summaries during preflight and is not used.

Evidence and structural validation **do not prove semantic truth**. ASR errors, ambiguous speaker identities, and translation errors can remain. In particular, malformed Japanese ASR is not silently repaired into a supposedly literal transcript. Minimal real Apple Kawasaki, Yodobashi Akiba and Bic Camera AKIBA excerpts dated 25 October 2026 are regression fixtures, explicitly labelled excerpts, with phone numbers, call IDs and personal identifiers omitted.

## Delivery, retries and uncertain outcomes

With `CALL_SUMMARY_FORMAT=v2`, the signed insight webhook saves the existing pending notification but does not run the long translation inside the 30-second post-response lifetime. The existing `*/10 * * * *` scheduled trigger processes one pending report per run. Scheduled execution has a longer lifetime; processing has an eight-minute deadline and the notification lease is ten minutes. This introduces up to ten minutes of normal notification delay, plus backlog/retries. Existing queue insertion and call correlation are unchanged.

D1's atomic claim prevents competing executions of the same summary row. Google Apps Script uses the **same SHA-256 call-ID deduplication key as v1**, so separate summary rows or redelivered events for one call do not resend mail, while distinct calls remain independent. V2 acknowledgements must include version 2 and the matching call ID; an old HTML sender cannot masquerade as v2. A failed v2 delivery never silently falls back to the legacy email.

MailApp has no provider idempotency key. To avoid duplicates across an uncertain crash, the script persists `sending_v2` before sending, then `yes` after success, under the script lock. If sending or acknowledgement is uncertain, automatic re-sending is blocked and the Worker records `SummaryDeliveryOutcomeUnknown`. This favors avoiding duplicates over guaranteed delivery. The operator must reconcile the exact call against Sent mail before manually changing that notification's property/status; never blindly clear the guard. This is not an exactly-once delivery guarantee.

## Deployment and rollback

1. Snapshot the currently deployed phone version/settings/schedules and Apps Script source/version privately. A latest-uploaded Worker artifact can differ from the deployed version; verify deployment IDs before selecting the source snapshot.
2. Run `node scripts/prepare-summary-release.mjs PHONE_SOURCE GAS_SOURCE PHONE_CONFIG PRIVATE_OUTPUT_DIR`, using the existing phone config with `keep_vars: true`.
3. Publish the Apps Script update as a **new version of the same deployment**, retaining the existing execution identity, recipient, access setting and secret property. Check its public GET capability `{ok:true,version:2,format:"call-summary-v2"}` and that an unauthenticated POST is rejected.
4. Verify the existing cron trigger. Run tests, type checks and dry-run bundling, then deploy **only `personal-phone-assistant`**, which already owns notifications. Set `CALL_SUMMARY_FORMAT=v2`; keep existing bindings/secrets. Do not deploy MCP/Auth/Voice for this feature.
5. Test with recorded data, a separate fixed test-notification ID, and an unmistakable `TEST — Call Summary v2` subject. A duplicate submission must not send a second email. No test call or production D1 test row is necessary.
6. Verify both text and HTML MIME parts and desktop/mobile layout. A mail-provider accepted/Sent copy is not by itself proof of delivery to the recipient inbox.

Rollback: restore the saved phone deployment version or set `CALL_SUMMARY_FORMAT` to legacy. Apps Script v2 retains the authenticated legacy handler, so it can remain deployed during rollback. If necessary, select its previous version (version 3 before this rollout) in the same deployment. Preserve deduplication properties, recipient, secrets, bindings, cron and all voice settings. Never replay already-delivered historical notifications to test rollback.

## Validation commands

`npm run typecheck`, `npm test`, `npm run test:phone-voice`, `npm run test:voice-edge`, `npm run build`, and a phone-specific Wrangler dry run using the private release config. CI runs the same repository checks on push. Tests cover successful/partial/unresolved/technical-failure outcomes, original Japanese translation, absent/partial transcripts, supported events, source/evidence validation, duplicate/concurrent notifications, uncertain MailApp outcomes, UTC/JST rollover, HTML safety, legacy acknowledgement rejection, and protected inbound/outbound boundaries.
